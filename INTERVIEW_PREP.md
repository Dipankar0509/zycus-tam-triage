# 🎓 Interview Preparation Guide: TAM Agentic Ticket Triage

This document is your complete cheat sheet for explaining the project during the technical interview and code walkthrough.

## 📌 1. Project High-Level Pitch (The "30-Second Elevator Pitch")

> *"In enterprise B2B software like Zycus, support tickets cannot be triaged using raw ticket text alone. A customer might report a seemingly minor issue, but if they are an enterprise customer with high ARR and an 'At Risk' churn health score, mishandling or delaying that ticket could lose millions in revenue.*  
> 
> *I built an autonomous **ReAct-based AI agent** that investigates support tickets just like a senior Technical Account Manager (TAM). Instead of running a static script or dumping thousands of articles into a massive prompt, the agent autonomously decides what lookups to perform: it resolves dirty or missing account records using fuzzy string matching, retrieves exact troubleshooting playbooks via BM25 retrieval, evaluates SLA tiers and churn signals, and produces a strictly validated Pydantic triage decision complete with an explainable step-by-step reasoning trace."*

## 🔑 3. Key Terminology You Must Know

| Term | What It Means & Why It Matters |
|---|---|
| **TAM (Technical Account Manager)** | A dedicated technical advisor assigned to enterprise clients. They proactively monitor customer health, ensure SLA compliance, and prevent churn. |
| **ARR (Annual Recurring Revenue)** | The annualized revenue generated by a subscription customer. A $240,000 ARR client gets far more urgency than a $10,000 ARR client. |
| **Account Health / Churn Risk** | Status of the account (`Healthy`, `At Risk`, `Churning`). If an account is `At Risk`, even low-severity bugs are escalated to the TAM. |
| **SLA (Service Level Agreement)** | Contractual response time commitments based on plan tier: `Enterprise` (1 hr for P1), `Business` (4 hr for P1), `Standard` (8 hr for P1). |
| **Priority Levels (P1–P4)** | **P1 (Critical):** Core production outage, zero workaround.  <br>**P2 (Major):** Critical workflow impacted with degraded performance. <br>**P3 (Moderate):** Minor feature issue with existing workaround. <br>**P4 (Low):** How-to questions, minor UI bugs, feature requests. |
| **Under-Triage** | The dangerous mistake of labeling a true P1 issue as P3/P4. This causes SLA breaches and angry customers. |
| **ReAct Loop (Reasoning + Acting)** | An agent architecture where the LLM alternates between **Thought** (reasoning what to do), **Action** (calling a tool), and **Observation** (reading tool output) until it reaches a conclusion. |
| **BM25 (Best Matching 25)** | A state-of-the-art probabilistic keyword ranking algorithm for text search. It prevents stuffing 100k tokens of KB into LLM prompts. |
| **Reasoning Trace** | The step-by-step audit log of every thought and tool call made by the agent. Crucial for explainability and auditing. |
| **Pydantic / Schema Validation** | A data validation library in Python. Guarantees the LLM's output matches the exact JSON schema required by downstream systems without syntax errors. |

## 💻 5. Technologies Used & Why We Chose Them

| Technology | Role | Why It Was Chosen |
|---|---|---|
| **Python 3.10+** | Core runtime | Standard in AI engineering and data science pipelines. |
| **Pydantic v2** | Data contract & validation | Enforces strict type validation on all triage outputs; eliminates malformed JSON. |
| **BM25 (Rank-BM25)** | KB search | Outperforms naive regex/keyword search; runs locally with zero embedding cost and sub-millisecond retrieval. |
| **Groq / Llama-3.3-70B** | LLM reasoning | Ultra-fast LPU inference (~200 tokens/sec), open-weights, free tier, excellent tool-use support. |
| **ReAct Framework** | Agent orchestration | Enables multi-step dynamic decision making without hardcoded sequences. |
| **Vanilla HTML/CSS/JS** | Mission Control Dashboard | Zero build step, runs instantly on any browser, highly responsive glassmorphism UI. |

## 🎯 6. Common Interview Questions & Model Answers

### Q1: "Why use an agent with tools instead of a single LLM prompt?"
> **Answer:**  
> *"Dumping 390 KB articles (~100,000 tokens) and 500 tickets into a single prompt is impractical: it is slow, expensive, and suffers from the 'needle-in-a-haystack' lost-in-the-middle problem. More importantly, real tickets require multi-step reasoning: first you discover the customer, which informs the search query for the KB, which in turn informs whether an SLA policy check is needed. An autonomous tool-calling agent only queries what it needs, keeping prompt sizes small, fast, and highly accurate."*

### Q2: "How does your agent handle dirty data, like missing `account_id`?"
> **Answer:**  
> *"In real enterprise datasets, account IDs are frequently blank or customers misspell company names (e.g. 'Cybertronics' vs 'Cybertronics Ltd.'). In `tam_agent/agent.py`, the `resolve_account` tool uses normalized fuzzy string matching. It strips legal suffixes (Inc, LLC, Ltd) and matches company names against `accounts.json` with a 90%+ match confidence."*

### Q3: "Walk me through how the agent triaged TKT-10005."
> **Answer:**  
> *"TKT-10005 was submitted by 'Cybertronics Ltd' reporting that new users cannot log in via SSO.  
> 1. In Step 1, the agent called `resolve_account` and discovered that Cybertronics Ltd is a **Business tier** client with **$240,000 ARR** whose account health is **At Risk**.  
> 2. In Step 2, it searched the KB for 'AnalyticsHub SSO configuration' and located the exact section explaining missing user group mappings in Identity Providers.  
> 3. In Step 3, it checked support policies for Business tier clients.  
> 4. Because SSO blocks all user access and the client is high ARR with an At-Risk health status, the agent correctly escalated this to **P1**, marked `tam_notification = True`, assigned it to TAM **Fatima Al-Rashid**, and routed it to **Identity & Security Engineering**."*

### Q4: "How would you scale this system to 30,000 tickets per month?"
> **Answer:**  
> *"At 10x scale, I would optimize across three pillars as documented in `SOLUTION.md`:  
> 1. **Cost:** Prompt caching on static tool definitions and system instructions reduces token costs by ~75%. With modern Flash models, 30k tickets cost under $15/month.  
> 2. **Latency:** Triage runs independently per ticket. Using an async queue (e.g. Celery or BullMQ) with 20 parallel workers, 30,000 tickets can be triaged in under 1 hour.  
> 3. **Retrieval Quality:** As the KB grows to 4,000+ articles, pure BM25 can miss synonyms. I would implement **Hybrid Search** (Dense Vector Embeddings + BM25 combined via Reciprocal Rank Fusion) with metadata pre-filtering by product area."*

### Q5: "How did you prevent infinite loops or runaway API costs?"
> **Answer:**  
> *"The agent loop has a hard limit of **5 iterations** (`MAX_TURNS = 5`). If the agent does not call `finalize_triage` within 5 turns, the system automatically falls back to a deterministic resolution using the gathered observations, guaranteeing bounded latency and cost."*
